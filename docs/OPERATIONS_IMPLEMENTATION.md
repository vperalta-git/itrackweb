I-TRACK operational fixes — 24 October 2026

Implemented in the existing web, Express/MongoDB and Expo applications:

- Mobile push: early foreground display handler, token refresh listener, retries and registration after resume/re-login, account ownership transfer, permission/settings flow, logout token removal, consistent Android channel configuration, persisted push tickets and a restart-safe receipt monitor. The notification screen can send a test and show actual provider status. Inbox records are saved before push dispatch; a queued ticket no longer counts as confirmed device delivery.
- Notification navigation: an authenticated, ownership-scoped target endpoint and role-aware web/mobile routes for driver allocations, preparations, bookings, stock and unit allocations. Web detail dialogs consume the record link. Mobile handles running-app taps, cold-start taps and deferred opening after login/password change. Removed or inaccessible records show a message and use the nearest authorized listing.
- First-login password change: mobile restores sessions through `/auth/me`, respects the server flag, blocks protected routes/back navigation and avoids preloading protected data until the password changes. Logout is sent while the session is still authenticated. Existing backend password validation and API enforcement remain authoritative.
- GPS: one publisher lives in the authenticated mobile shell instead of each trip screen. The watcher starts before the initial high-accuracy request; fresh stationary heartbeats, bounded upload frequency, resume recovery, sample timestamps and optimistic update checks prevent stale/out-of-order writes. Small stationary jitter does not move the stored vehicle. Speed conversion uses metres/second from Expo. Fabricated mobile vehicle positions and initial percentage progress were removed. The existing web road ETA and GPS outage classifications remain in use; polling is faster, pauses when hidden and does not overlap.
- Destructive actions: common reason/review dialogs on both clients; server enforcement for operational deletions, cancellations, deactivations and trip stop/rejection decisions. Reasons support Unicode and multiple lines. An authenticated audit intent is stored before mutation and its outcome is finalized before success is acknowledged. A failed finalization leaves a durable pending entry and warns the caller to refresh before retrying.
- Audit: persistent actor, account role, entity, action, timestamp, before/after summaries and reason. Covers create/update/delete/cancel, assignment/allocation, driver acceptance, rejection requests/reviews, status/approval decisions and PDF generation/print requests. Existing authentication events are included. Web and management mobile reports read server audit entries. PDF logging describes generation or opening the print dialog; it cannot establish that a user saved or printed the PDF.
- Last login: successful credential validation records `User.lastLoginAt`; the directory returns it and falls back to real historical login events for older accounts.
- Driver workflow: atomic assigned-driver acceptance; rejection requests require a driver-entered reason and retain the booking until an admin/supervisor approves. Duplicate/stale decisions are blocked, drivers cannot cancel directly, approvers/driver are notified and both web/mobile management expose review actions and outcomes.
- Monitoring: a paginated driver table replaces the map-heavy monitoring section, keeps urgent GPS outages red and includes active directory drivers without a current delivery for administrators/supervisors. Details and driver history open in a modal. Serious delay history uses recorded start plus a positive planned duration and the recorded completion time or current uncompleted state; events exceeding the two-hour allowance are saved and preserved through later GPS analysis. No cause or driver fault is inferred.
- Listing UI: functional web/mobile dashboard entry cards, stock status/allocation/preparation filters, a responsive model grid with counts and model filters, pagination for driver monitoring/delay history and mobile notifications/trip/dispatch history, and table pagination that remains usable during live refreshes. Existing paginated operational lists are reused.

Files changed are grouped around existing modules: web dashboard/inventory/booking/preparation/allocation pages, navbar, shared dialogs/table/PDF helper and notification/audit libraries; backend controllers/routes/models plus focused audit, notification-target, push-receipt and delay-history services; mobile authentication/app/tracking contexts, shared GPS and notification helpers, driver/admin screens, reports, pagination and Android channel configuration. The web repository includes synchronized backend/mobile sources; their separate repositories receive the corresponding releases.

Validation passed: web/mobile TypeScript; production Next.js build from a clean publishing checkout; Expo production Android and iOS Hermes bundle exports; 66 backend module import/export links and backend JavaScript syntax; 6 operational UI tests, 12 backend operational tests, 8 authentication tests, 3 API/GPS outage tests, 13 authorization/workflow tests, 4 delivery-monitoring tests, 2 road-ETA tests, 3 PDF/report tests and 4 audit-role tests; the focused tracking table/modal smoke test; and the built-server HTTP authentication smoke test using isolated local fixtures. No long or unrelated test suite was run. Final commit hashes are reported with the handoff.

Verification limits and rollout:

- Physical-device push receipt/display and GPS hardware were not available in this workspace. Install a newly built native app, use Notifications → Send test push, check receipt status after Expo's receipt delay, and verify foreground/background/terminated-app display and tapping on the actual phone. Required FCM v1/APNs credentials live in the Expo project and cannot be validated by a JavaScript bundle build. The API reports provider credential errors instead of treating an inbox insert as delivery success.
- Android/iOS exports compile production JavaScript/Hermes bundles. They do not produce a newly signed APK/AAB/IPA or install an app. Native builds must include the updated channel/manifest settings. Location publishing remains foreground Expo tracking; OS suspension or force-stop is not background tracking support.
- Database writes and provider calls were tested with isolated repositories/fixtures, without mutating production customer data. New MongoDB schema fields are additive. Deploy the backend together with the clients so `/audit-events`, notification targets/status and driver acceptance/rejection endpoints exist.
- Audit display currently loads the newest 2,000 operational entries plus 1,000 authentication events and paginates/filters that window. Historical browser-only audit entries cannot be recovered from other browsers. Existing local entries remain available on web. Older serious delivery delays can be calculated only when real trip timestamps and planned duration exist; they are labelled as calculated, not historical observations.
- The standalone backend release retains the authorization/validation and recent GPS/ETA prerequisites already present in the web repository's main branch. The original dirty workspaces are preserved; publishing checkouts use current remote main and normal, non-forced pushes.
