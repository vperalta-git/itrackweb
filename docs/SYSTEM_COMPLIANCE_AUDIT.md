## C. Detailed Findings

### SC-01 - Add Functionalities

1. **Current implementation:** Real modules exist for authentication, profiles, stock CRUD, unit-agent allocation, driver trips, preparation/dispatch checklists, test drives, notifications, reporting and dashboards. This is substantially more than a screen prototype.
2. **Frontend:** Web role routing connects actual pages in `frontend/app/[role]/[[...slug]]/page.tsx:25`. Mobile route groups reuse business screens, e.g. `mobile/app/(tabs)/(supervisor)/vehicles.tsx:1`; role visibility is described in `mobile/src/mobile/navigation/access.ts:262`.
3. **Backend:** `backend/src/routes/index.js:39` mounts auth, users, vehicles, allocations, preparations, test drives, notifications and setup endpoints. Business controllers perform Mongoose operations and integration calls.
4. **Database:** `User`, `AuthSession`, `Vehicle`, `UnitAgentAllocation`, `DriverAllocation`, `Preparation`, `TestDriveBooking`, `Notification`, `PreparationEtaArtifact`, `AuthEvent`, and `UserAuditEvent` models are available. Server bootstrap lists most operational collections (`backend/src/server.js:18`); no database connection was made during this audit.
5. **Roles:** All six API/mobile roles; four web roles. UI restrictions differ by module as listed in A. The API primarily enforces authenticated active-account access, not the frontend role policy.
6. **Evidence of functionality:** 19 existing isolated tests pass. Data adapters call real mounted routes; focused printing, OTP/email and model checks execute real application functions with external operations replaced by fixtures.
7. **Broken/incomplete:** User and vehicle controllers have no actor-role gate; focused mocks reproduce unauthorized user role/password update and vehicle deletion. The analytics “Export Report” button has no handler (`frontend/app/(dashboard)/reports/vehicles/page.tsx:273`). Settings save persists notification preferences only, while system/SMTP controls and Clear Cache/Export Data/Reset Settings buttons are disconnected (`frontend/app/(dashboard)/settings/page.tsx:46`, `:494`, `:510`). Unit setup is browser-local on web and process-memory on mobile, with no shared backend catalog (`frontend/lib/unit-setup-data.ts:239`, `mobile/src/mobile/data/unit-setup.ts:260`). Web TypeScript fails and `frontend/next.config.mjs:69` suppresses build type errors.
8. **Verification limit:** Passing auth tests does not verify every visible button or a deployed workflow. Provider/device/browser/database behavior remains outside this local audit.
9. **Classification: FAILED.** Confirmed authorization failures and inert advertised actions violate the requirement for connected, role-appropriate functionality. This does not mean every module is broken.
10. **Recommended fix:** Prioritize backend permissions and stock/password integrity, then connect the specifically identified controls, persist shared configuration, and resolve type errors. Preserve existing connected workflows.

5. **Roles:** History: A/S/M/SA; audit and vehicle/allocation analytics: A/S. Mobile A/S/M/SA report profiles expose PDF sharing, not a verified native physical-print workflow.

### SC-03 - SMS Notification (Objective #4)

1. **Current implementation:** Preparation completion/release transitions trigger backend SMS. Provider branches exist for UniSMS, Fortmed, FMCSMS and Twilio; this is an actual server integration, not only an SMS label.
2. **Frontend:** Web Ready for Release calls the preparation status adapter (`frontend/app/(dashboard)/preparation/page.tsx:566`, `frontend/lib/preparation-data.ts:454`). Mobile preparation/checklist updates use the same backend resource.
3. **Backend:** Preparation create/update calls `dispatchPreparationCompletionSmsTask` (`backend/src/controllers/preparationsController.js:651`, `:761`). The worker checks status/contact/previous send, atomically claims dispatch, calls `sendPreparationCompletionSms`, and records success/error (`:312`, `:372`, `:400`). Provider code is in `backend/src/services/smsService.js:578`.
4. **Database:** `Preparation.completionSmsSentAt`, `completionSmsDispatchStartedAt`, and `completionSmsLastError` are persisted (`backend/src/models/Preparation.js:147`). Provider message IDs/status/receipts are not persisted with that record.
5. **Roles:** A/S web/mobile release management controls; DP checklist processing may change preparation status. Customer is the SMS recipient, not an additional system role. Actor permission checks are insufficient at the API.
6. **Evidence of functionality:** Configured providers build HTTP requests with normalized Philippine recipient formats and a release message. Disabled/unconfigured paths return a skip. HTTP errors are caught; claims are cleared and last error saved. No real SMS was sent.
7. **Missing/broken:** UniSMS accepts any HTTP-success body (`backend/src/services/smsService.js:544`), including a synthetic `{success:false}` fixture. `completionSmsSentAt` records request success, not handset delivery. No delivery callback/status polling, durable retry worker, timeout, or stale-claim recovery was found. Trigger requires a status change (`preparationsController.js:348`), so editing/retrying the same state does not resend after failure. A crash after claim can leave dispatch blocked. Both `completed` and `ready_for_release` are eligible; the message always says ready for release, so ordering/meaning must match the actual business event. Raw customer phone details also appear in preparation dispatch logs (`:320`, `:397`).
8. **Verification limit:** Real response contracts, provider account configuration, quota, sender approval, carrier acceptance and handset delivery were not tested. The synthetic HTTP fixture proves the current validation behavior only.
9. **Classification: PARTIALLY IMPLEMENTED.** Event wiring, send adapters and basic failure persistence are present; reliable delivery-result processing/recovery is incomplete.
10. **Recommended fix:** Validate each provider contract, persist provider reference plus accepted/delivered/failed distinction, make retries recoverable and visible, and mask contact logs. Do not rebuild the provider adapters or send a real message as part of this audit.

### SC-04 - Shipment Tracking (Objective #1)

1. **Current implementation:** Shipment is represented by `DriverAllocation`, with a vehicle, driver, pickup/destination, planned schedule, status, actual start/end and location. The lifecycle supports pending, assigned, in transit, delivered, completed and cancelled.
2. **Frontend:** Web allocation and tracking pages are connected through `frontend/lib/driver-allocation-data.ts:199`. Mobile driver accept/start/end handlers call shared allocation functions (`mobile/app/(tabs)/(driver)/dashboard.tsx:337`, `:362`, `:387`). Web monitoring polls every 15 seconds (`frontend/app/(dashboard)/allocation/drivers/tracking/page.tsx:162`).
3. **Backend:** `POST/PATCH /api/driver-allocations`, live-location, completion-request and stop-request endpoints are mounted in `backend/src/routes/driverAllocationsRoutes.js:17`. Controller checks selected driver role, referenced records and active-allocation conflicts (`backend/src/controllers/driverAllocationsController.js:238`, `:342`). Lifecycle updates derive timestamps/duration and reconcile vehicle status (`:300`, `:451`).
4. **Database:** `DriverAllocation` references `Vehicle`/`User` and stores schedule/location/state; indexed fields are defined in `backend/src/models/DriverAllocation.js:289`. No separate shipment model is necessary to establish this implementation.
5. **Roles:** A/S allocate/manage; M/SA monitor; DR executes trip actions. DP's primary workflow is preparation/checklist, not the web driver-allocation management screen.
6. **Evidence of functionality:** UI -> adapter -> mounted API -> Mongoose persistence path exists; planned and actual timestamps remain distinct. Existing tests cover loss-of-GPS alert behavior, not a complete shipment/arrival integration run.
7. **Missing/broken:** General status update accepts any enum-valid next status without an enforced transition graph or assigned-driver/approver checks. Vehicle/driver conflict checks are query-then-write, with no atomic active-assignment constraint. Driver allocation reconciliation can mark a unit available without considering preparation state (`driverAllocationsController.js:285`). The inverse preparation reconciler ignores active shipment state (`preparationsController.js:233`). Arrival/completion is not established by a trusted server-side dealership/geofence check; client controls and editable destinations are not proof of physical arrival. Location fallback and refresh gaps are shared with SC-13/SC-19.
8. **Verification limit:** No dispatch-to-dealership physical journey, concurrent allocation, or real database update was exercised. The implementation supports arbitrary destinations, not a verified exclusive dealership destination.
9. **Classification: PARTIALLY IMPLEMENTED.** A substantial connected lifecycle exists, but trusted transitions, consistency and real-arrival verification are incomplete.
10. **Recommended fix:** Enforce actor/assignment permissions, legal transitions and concurrency protection; reconcile one authoritative vehicle state across preparation and shipment; verify a sample shipment through arrival using approved test records later.

3. **Backend:** `POST /api/users` handles optional generation/provided password, hashes it, sets `mustChangePassword:true`, calls email, and attempts compensating deletion on send failure (`backend/src/controllers/usersController.js:238`). `backend/src/services/emailjsService.js:53` sends the HTTP request and translates provider/network/configuration errors; `:137` builds welcome credential parameters.
4. **Database:** User account persists in `User`; only the hash is stored for login. There is no persistent per-account email delivery-status record. The generated password is supplied to the email provider, as expected for the implemented credential-email design; no real password is included in this audit.
5. **Roles:** A/S account-management UI creates accounts; all six account roles may receive the email. The API's missing management-role enforcement is critical shared work, not an intended permission for other roles.
6. **Evidence of functionality:** Isolated account-create check verified first-login flag, email call and rollback call after rejection. 7. **Missing/broken:** No disconnected standard form trigger was found. Backend `sendCredentialsEmail` defaults false, allowing another API caller to opt out; whether email must be mandatory for every account creation should be explicitly decided. Welcome template falls back to the OTP template if not configured, which may not render account fields. `getClientLoginUrl` assumes one `CLIENT_ORIGIN`; a comma-separated CORS origin list would generate an invalid single login URL (`emailjsService.js:98`). Rollback is compensating deletion, not transactional delivery and may fail; no resend/delivery-status UI was found. Temporary password generation uses `Math.random` (`backend/src/utils/passwords.js:15`), so stronger generation is advisable.
8. **Verification limit:** No provider request, dashboard template, spam/inbox receipt or deployed login link was tested. A successful HTTP acceptance cannot certify inbox delivery.
9. **Classification: PASSED for the configured registration-email implementation.** Both standard forms trigger a real service with meaningful payload/error handling; live template/inbox verification remains open. This is not an approval of the shared authorization gap.
10. **Recommended fix:** Preserve the integration, restrict account management, use a dedicated confirmed welcome template and single public login URL, and consider secure password generation/resend/status handling. Verify delivery later with explicitly authorized test accounts.
